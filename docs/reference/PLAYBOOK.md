# Плейбук на 3 дня

**Сначала правила:** `docs/RULES.md` (очно, быть не позднее 11:00 каждого дня, код на GitLab, вклад каждого, защита всей командой, апелляции нет). Что делать в первые часы после получения кейса — в `docs/KICKOFF.md`; GitLab CI — `docs/GITLAB.md`.

Принцип: **баллы за час**. У команды ≈15 часов чистой работы на человека (расчёт — в `ANALYSIS.md`).
Сначала то, что стабильно даёт баллы и не даёт штрафов; красота и «фичи сверх» — только потом.

## Приоритеты

### Обязательно (иначе штраф или ноль в блоке)
1. **Задеплоено и открывается по ссылке** (без этого −20%). Первый деплой — в первые 2–3 часа, пустым каркасом.
2. **Минимум из кейса** выполнен целиком (без этого −30%). Выписать его в первый час в `docs/CASE.md`.
3. **Главный сценарий кейса проходит от начала до конца** без ошибок, на демо-данных.
4. **Проверка занимает минуту:** демо-аккаунты, демо-данные, README «Как проверить», Swagger, CI зелёный.
5. **Презентация загружена до 15:00 третьего дня** и репетиция демо.

### Нужно (самые дешёвые баллы Backend, которых нет у большинства)
- Схема данных (ER) и миграции — в шаблоне, правите под кейс.
- Unit-тесты на каждое правило + интеграционные + хотя бы 2 негативных. Отчёт покрытия виден в CI.
- Описание доменного процесса (диаграмма статусов) в `docs/ARCHITECTURE.md`.
- Один главный показатель продукта (North Star) и честная формула — `/api/stats` уже считает пример.

### По возможности (только после «обязательно» и «нужно»)
- Дополнительные функции, которые закрывают конкретную потребность пользователя из кейса (1–2, не 10).
- Рекомендации, статистика, экспорт CSV, красивые состояния пустого экрана.

### НЕ делать
Из реальных формулировок «что не нужно делать» в кейсах + моё суждение для 3 дней:

| Не делать | Почему |
|---|---|
| Авторизацию, если кейс её не просит (в Wellness-кейсе она прямо отсутствует) | съедает 1–2 часа, баллов не даёт; в шаблоне её можно отключить, оставив одного «текущего пользователя» |
| Реальную оплату, доставку, банки, e-mail/SMS, push, чат, карты, геолокацию, календарь | кейсы запрещают; эмулируйте заглушкой |
| Сложный ML и «умные» рекомендации | кейсы запрещают; правило «похожие по категории» достаточно |
| Идеальную админку | нужна минимальная: список + смена статуса |
| Микросервисы, Kubernetes, Redis, брокеры, GraphQL, WebSocket | у жюри нет критерия, у вас нет времени |
| Свою дизайн-систему и анимации | хватит шаблона; потратьте время на состояния ошибок и пустого экрана |
| 100% покрытие тестами | жюри смотрит на ключевые сценарии и негативные кейсы, а не на процент |
| Refresh-токены, OAuth, подтверждение почты | вынесите в «известные ограничения» в документе (простая защита входа от перебора в шаблоне уже есть) |
| Мобильное приложение, если нет мобильного разработчика | лучше хороший веб + адаптивность |
| Переписывать шаблон «как удобнее» | у шаблона уже зелёный CI; каждое переписывание — риск и часы |

## Роли в команде (3–5 человек)

| Роль | Отвечает за |
|---|---|
| Бэкенд | сущности, правила, тесты, миграции, `docs/ARCHITECTURE.md` |
| Фронтенд | экраны по сценариям, валидация, состояния, адаптивность |
| Платформа (может быть бэкендер) | сервер, CI/CD, секреты, demo-данные, `preflight.sh`, **деплой после каждого merge** |
| Продакт/презентация | кейс, минимум, метрика, user stories, слайды, речь |
| Дизайн/UX (если пятый) | прототип до кода, консультация UI/UX, финальная полировка |

В команде из трёх: бэкенд+платформа, фронтенд, продакт+презентация. **Деплой и тесты не должны остаться «по остаточному принципу».**

## Правила, которые экономят часы

0. Красный линтер (`ruff`/`oxlint`) деплой **не блокирует**; чинится командой `make fmt`. Тесты и сборка блокируют.
1. Один человек владеет `main`. Ветки короткие; больше двух часов без merge — плохой знак.
2. Если что-то не получается 30 минут — упрощайте (заглушка), а не копайте глубже.
3. Каждый вечер: `scripts/preflight.sh` на проде и список «что сломалось».
4. Не меняйте имена полей API без предупреждения фронтенда: контракт — Swagger и `frontend/src/types.ts`.
5. Секреты — только в GitHub Secrets и `.env`, никогда в репозитории.
6. Данные кейса (датасет, список товаров) кладите в `backend/app/seed.py` / `data/` и загружайте при старте.

## Рецепты типовых модулей на этом шаблоне

Оценки времени — мои допущения для одного разработчика.

| Нужно | Как собрать из шаблона | ≈ |
|---|---|---|
| **Витрина** (каталог, корзина, заказ) | модели `Product`, `Order`, `OrderItem` (по образцу `Item` + `ItemEvent`); фильтры/поиск уже есть в `ItemRepository.search`; итог корзины считать на бэкенде | бэк 2–3 ч, фронт 3 ч |
| **Очередь/лимиты/таймеры** (GPU, привилегии) | модель `Booking(resource, user, starts_at, ends_at, status)`; позиция в очереди — запрос по `status='queued' ORDER BY id`; «машина времени» — параметр `now` в сервисе вместо `datetime.now()` | 3 ч |
| **QR/коды** (MeetPoint) | у события — короткий `join_code`; на фронте QR рисуется библиотекой `qrcode`; взаимный интерес — таблица `Like(a, b)`; контакт отдаём, только если есть встречный | 2–3 ч |
| **Расчёт по датасету** (тариф, зарплата) | CSV кладётся в `data/`, грузится при старте; функция расчёта в `services/`; unit-тесты на неё; «real/restored» — поле в ответе | 2 ч |
| **Отключить авторизацию** | оставить зависимость `get_current_user`, но возвращать фиксированного пользователя; убрать `AuthPage` | 30 мин |
| **Рекомендации** | «похожие по категории и цене» одним запросом; не нейросеть | 1 ч |

## Переименование `Item` в сущность кейса: чек-лист на один экран
Делайте по порядку и после каждого шага запускайте `make test` (тесты подскажут, что забыли):

1. **Модель** — `backend/app/models.py`: класс `Item` (+ таблица, поля, индексы), при необходимости `ItemEvent`.
2. **Миграция** — `make migration m="rename item to offer"`, проверьте файл в `backend/alembic/versions/` (переименование таблицы autogenerate не угадывает: пишите `op.rename_table` руками, пока в БД нет данных можно пересоздать).
3. **Схемы** — `backend/app/schemas.py`: `ItemCreate/Update/Out/List`, статусы и действия (`Status`, `Action`).
4. **Правила** — `backend/app/services/items.py`: таблица `RULES` и проверки доступа; затем `repositories/items.py`.
5. **Роутер** — `backend/app/routers/items.py`: пути (`/items` → `/offers`) и `main.py` (подключение).
6. **Сводка** — `backend/app/services/stats.py`; демо-данные — `backend/app/seed.py`.
7. **Тесты** — `backend/tests/*`: подставить новые имена и правила; тесты на каждое правило оставить.
8. **Фронтенд** — `frontend/src/types.ts`, `api.ts` (пути), `labels.ts` (подписи статусов и действий), компоненты `ItemsPage`, `ItemModal`, `ItemForm`.
9. **Документы** — `docs/ARCHITECTURE.md` (ER-диаграмма, процесс, API) и `README.md`.

Подсказка: если сущностей несколько, не переименовывайте `Item`, а копируйте цепочку «модель → схема → сервис → роутер → тест» для каждой новой.

## Презентация: 7 слайдов на 5 минут

1. Проблема и пользователь (кто, какую боль решаем) — 30 с.
2. Решение и **демо** живого сценария на продакшене — 1,5 мин (запасной вариант: видео).
3. User story / путь пользователя — 30 с.
4. Бизнес-ценность: **North Star метрика и как её считаем**, формула и пример на демо-данных — 45 с.
5. Архитектура: схема, слои, БД; почему так — 45 с.
6. Качество: тесты, CI/CD, зелёный пайплайн, логи — 30 с.
7. План развития с приоритетами (что сделали, что дальше и почему в таком порядке) — 30 с.

Структура слайдов оценивается отдельно: не перегружайте текстом, показывайте работу продукта. Запасной план: видео демо и скриншоты на случай проблем с интернетом.
