# Деплой

**Недеплой = −20% баллов** (получили 41–61% команд в прошлых хакатонах).

**Статус: выдадут ли сервер на хакатоне — не подтверждено.** Поэтому план из трёх ступеней, и первые две можно сделать уже сейчас:

| Ступень | Что | Когда решить |
|---|---|---|
| 1. Уточнить | Спросить организаторов (в чате участников после регистрации или по почте из приглашения): «Выдаётся ли сервер/хостинг для деплоя? Какой — VM с SSH, PaaS? Нужно ли что-то привезти?» | **сегодня-завтра** |
| 2. Свой запасной сервер | Если ответ «нет» или «не знаем» к 14 октября — взять дешёвый VPS на неделю (это ваше решение и ваши деньги). Оба скрипта проверены, см. ниже | 14 окт |
| 3. Аварийно: ссылка с ноутбука | `make tunnel` даёт публичный HTTPS-адрес на ваш локальный стек за 10 секунд. Это **не настоящий деплой**: ноутбук должен быть включён и онлайн, адрес меняется при каждом запуске, а засчитает ли жюри такое как «деплой» — неизвестно. Только если всё остальное не вышло | на хакатоне |

Что проверено на практике (в контейнерах Ubuntu 24.04 на этом ноутбуке, не на настоящем хостинге):
- `scripts/deploy-manual.sh` — rsync, `.env` с правами 600, сборка и запуск стека по SSH, нестандартный порт SSH, свои пароли; после деплоя все 10 проверок `preflight.sh` зелёные.
- `scripts/bootstrap-server.sh` — создание пользователя `deploy`, ключ, группа `docker`, повторный запуск ничего не дублирует.
- `make tunnel` — адрес вида `https://….trycloudflare.com` открывает приложение из интернета.

Не проверено: установка Docker скриптом `get.docker.com` и настройка файрвола `ufw` на настоящем сервере, автодеплой из GitHub Actions (нужен сервер), работа с конкретным PaaS.

## Если сервер выдают: что спросить у менторов/организаторов (первые 30 минут)

| Вопрос | Зачем |
|---|---|
| Что именно выдают: виртуальная машина (VM) с SSH, готовая платформа (PaaS), доступ в Kubernetes? | выбор пути ниже |
| Как подключаться: IP, пользователь, ключ или пароль? Есть ли root/sudo? | `ssh` и установка Docker |
| Установлен ли Docker и docker compose? Можно ли ставить? | без Docker — путь «без контейнеров» (см. ниже) |
| Какие порты открыты снаружи (80/443/8080)? Есть ли домен и HTTPS? | `PORT` в `.env` |
| Видит ли сервер интернет (docker pull, pip, npm)? Достучится ли до него GitHub Actions? | выбор: автодеплой из CI или ручной |
| Где взять БД: свою Postgres в compose или выдают? | `DATABASE_URL` |
| Сколько ОЗУ/диска? | хватит ли на сборку на самом сервере |
| До какого времени сервер живёт после защиты? | жюри может проверять позже |

## Путь 1. VM с SSH и Docker (самый вероятный)

**1а. Автодеплой из CI** — если GitHub Actions достучится до сервера (публичный IP):
1. На своём ноутбуке: `ssh-keygen -t ed25519 -f ~/.ssh/prod_deploy -C prod-deploy`
2. Если пользователь без Docker: скопируйте `scripts/bootstrap-server.sh` на сервер и запустите под root: `bash bootstrap-server.sh "<содержимое prod_deploy.pub>"` — ставит Docker, создаёт пользователя `deploy`, включает файрвол. Если вам дали готового пользователя — просто добавьте `prod_deploy.pub` в его `~/.ssh/authorized_keys` и убедитесь, что `docker ps` работает без sudo.
3. GitHub → Settings → Secrets and variables → Actions:
   - Variable `DEPLOY_ENABLED` = `true`
   - Secrets: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` (приватный ключ), `POSTGRES_PASSWORD`, `SECRET_KEY` (длинная случайная строка), `ADMIN_PASSWORD`
4. Если нужен не порт 80, поправьте `PORT` в шаге `Deploy` workflow (`.github/workflows/ci.yml`) и в проверке после деплоя.
5. Пуш в `main` → `http://<IP>/` и `/api/docs`. Проверка: `ADMIN_PASSWORD=... scripts/preflight.sh http://<IP>`.

**1б. Ручной деплой с ноутбука** — если CI до сервера не достучится (закрытая сеть, VPN, NAT) или нужно срочно:
```bash
scripts/deploy-manual.sh deploy@<IP>            # порт 80
PORT=8080 scripts/deploy-manual.sh deploy@<IP>  # другой порт
```
Скрипт копирует проект на сервер (rsync) и запускает там `docker compose up -d --build`. Сборка идёт на сервере: нужно ≥2 ГБ ОЗУ и доступ сервера в интернет.
Секреты для публичного стенда: `POSTGRES_PASSWORD=... SECRET_KEY=... ADMIN_PASSWORD=... scripts/deploy-manual.sh ...`.

## Путь 2. Готовая платформа (PaaS) или Kubernetes
- Спросите, как деплоить: часто это «подключите Git-репозиторий» или `docker push` в их реестр.
- Бэкенду нужны переменные: `DATABASE_URL` (`postgresql+psycopg://user:pass@host:5432/db`), `SECRET_KEY`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `SEED_DEMO`.
- Образы: `backend/Dockerfile` и `frontend/Dockerfile`. Фронтенд (nginx) проксирует `/api` на хост `backend` — на платформе замените его на адрес бэкенд-сервиса в `frontend/nginx.conf`.
- Если БД выдают отдельно, уберите сервис `db` из `docker-compose.yml`.

## Путь 3. Нет Docker и поставить нельзя
Запасной вариант без контейнеров: бэкенд — `pip install -r backend/requirements.txt && alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000`
(БД — SQLite по умолчанию, для хакатона допустимо); фронтенд — `npm ci && npm run build`, статику из `frontend/dist` отдать любым веб-сервером, `/api` проксировать на `:8000`.
Это дольше и хрупче: используйте, только если Docker недоступен.

## Что подготовить заранее (без сервера)
1. **Docker Desktop на ноутбуке** — проверить `docker compose up -d --build` локально и убедиться, что открывается `http://localhost:8080`; запустить `scripts/preflight.sh`. Это репетиция деплоя без сервера. (В CI это уже проходит, но на ваших машинах — нет.)
2. SSH-ключ деплоя сгенерировать заранее (шаг 1а.1), чтобы на хакатоне не тратить время.
3. Скрипты `bootstrap-server.sh` и `deploy-manual.sh` проверены в контейнерах Ubuntu (см. выше). Если найдётся любая настоящая Linux-машина, прогоните на ней: останется непроверенной только установка Docker и `ufw`.
4. Если организаторы заранее сообщат тип сервера — напишите сюда, подготовим точный сценарий.

## Путь 4. Свой VPS (если организаторы сервер не дают)
Любой Ubuntu 22.04/24.04 с 1–2 ГБ ОЗУ; домен не нужен (`http://<IP>`). Дальше — Путь 1: `bootstrap-server.sh` под root, затем автодеплой (1а) или `deploy-manual.sh` (1б).
Если хостер даёт готовую панель файрвола, запускайте `SKIP_FIREWALL=1 bash bootstrap-server.sh "<ключ>"`.

## Путь 5. Аварийно: временная ссылка с ноутбука
```bash
make up        # стек на localhost:8080
make tunnel    # печатает https://….trycloudflare.com (Ctrl+C - остановить)
```
Работает через Docker (Cloudflare quick tunnel), ничего ставить на Mac не нужно, аккаунт не нужен.
Ограничения: ноутбук включён и онлайн всё время проверки; адрес новый при каждом запуске (его нужно указать в README и презентации); стабильность не гарантируется.
Используйте как «лучше, чем ничего», и сообщите жюри честно, что это временная ссылка.

## Нюансы
- Демо-данные (`SEED_DEMO=true`) — плюс для жюри, но пароли демо-аккаунтов публичны: не храните на стенде ничего ценного.
- HTTPS в шаблон не включён (для хакатона достаточно HTTP). Если организаторы выдают домен — поставьте Caddy перед nginx.
- Пока деплой не заработал, **не пишите фичи вслепую**: первым деплоем должен стать пустой каркас, потом всё остальное.
