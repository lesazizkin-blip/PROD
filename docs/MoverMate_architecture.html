1. Что делает система и какие у неё ограничения

Пользователь создаёт проект переезда (название, дата, адреса необязательны), составляет план задач на три этапа (до, в день, после; типовые задачи — по кнопке), заводит коробки с комнатой назначения, быстро вписывает содержимое, печатает этикетки с QR-кодом, отмечает погрузку, доставку и распаковку коробок, ведёт статус каждой вещи (упакована, распакована, найдена, потеряна, повреждена) и ищет вещи по названию. Если вещь потерялась, система подсказывает, в каких нераспакованных коробках её искать. Помощники присоединяются к проекту по ссылке-приглашению.

2. Общая схема

Рис. 1. Слои системы. Сайт и сервер едут в одном образе, база лежит в томе.

Сайт и API работают на одном origin: Caddy отдаёт сайт и проксирует /api на FastAPI, поэтому CORS не нужен. В режиме разработки запросы /api проксирует Vite (порт 5173 на порт 8000).

3. Сервер (backend)

Три слоя с чёткими обязанностями: роутер принимает и проверяет запрос, сервис содержит все правила и работает с транзакцией, модель описывает таблицы. Бизнес-правил в роутерах нет, поэтому сервисы можно тестировать без HTTP.

4. Модель данных

Рис. 3. Таблицы и связи. Миграции: backend/alembic/versions/ — 0001 схема, 0002 время и категория задач, 0003 пользователи и доступ, 0004 статус вещи вместо флажка «потеряна», 0005 пометка «вещь первого дня».
  • Номер коробки хранится отдельным числом, а не как id. Сервер выдаёт max(number)+1 внутри проекта под блокировкой строки проекта; при гонке запись повторяется до трёх раз, а UNIQUE не даёт создать дубль. Ограничение: номер удалённой последней коробки будет выдан снова.
  • Статус вещи — строка packed | unpacked | found | lost | damaged; в ответе API для совместимости есть и lost = (status == "lost"). Миграция 0004 перенесла старый флажок «потеряна» в статус и откатывается обратно.
  • name_norm в вещах: имя без регистра, ё = е, схлопнутые пробелы. Поиск не зависит от функций СУБД и одинаково работает на SQLite и PostgreSQL.
  • Комната это строка в коробке: у комнаты нет своих атрибутов, прогресс по комнатам считается группировкой.
  • Индексы: boxes(project_id, room, status), items(box_id), items(name_norm), tasks(project_id, stage), events(project_id, id), project_members(project_id, user_id) (уникальный, проверка доступа в каждом запросе).
  • Справочники (task_templates, tips) сидятся при каждом старте и добавляют только недостающее.

Доступ: пользователи, сессии, участники, приглашения

Стрелка — «один ко многим». В базе нет ни одного открытого пароля или токена: утечка БД не даёт войти и присоединиться к проекту.

5. Доменная логика: статусы коробки и вещи

Рис. 4. Машина статусов. Таблица переходов: TRANSITIONS в services/boxes.py.

Проверка переходов вынесена в чистую функцию check_transition и покрыта тестом на все пары статусов: разрешён только следующий этап. Ошибочную отметку исправляет отдельная ручка status-corrections: только назад, с причиной, событие box.status_corrected с автором. Смена статуса, запись в журнал и проверки идут в одной транзакции со SELECT … FOR UPDATE по коробке: две одновременные отметки идут по очереди. Массовая отметка комнаты (bulk-transitions) атомарна: одна недопустимая коробка отклоняет всю операцию.

На сайте статус меняется в окне «Сменить статус»: показаны все пять статусов с пояснением, доступен следующий этап; недоступные объясняют, что отметить сначала.

Статус вещи

У каждой вещи свой статус: упакована (по умолчанию), распакована, найдена, потеряна, повреждена. В отличие от коробки, переходы свободные: вещь может найтись или оказаться повреждённой в любой момент. Статус выбирается в окне по клику на цветную метку вещи. Каждая смена пишется в журнал (item.lost, item.found или item.status_changed с «из» и «в»); для потерянных вещей работают подсказки, где искать.

Правила, на которых держится сервис

ОбластьПравило

Как работают экраны

  • Каждый экран грузит данные через useAsync и показывает единые состояния «загрузка / ошибка с повтором / пусто» (StateView). Действия пользователя ловят ошибки сервера и показывают понятный текст.
  • Клиент API (api/client.ts) ходит на /api того же origin, ставит таймаут 20 секунд, разбирает формат ошибок сервера и превращает ответ nginx в HTML (502) в понятное сообщение.
  • Без входа любой адрес показывает экран входа, а адрес не меняется: после входа открывается та же страница (коробка по QR, приглашение). Список проектов приходит с сервера; в localStorage запомнен только выбранный проект, после выхода список стирается.
  • QR: этикетка кодирует обычную ссылку {origin}/projects/{pid}/boxes/{n}; QR рисуется в браузере (qrcode.react). Любая камера телефона открывает её; на сайте есть и свой сканер, который принимает ссылку с любым адресом сайта.
  • Печать: window.print() и правила @media print оставляют только этикетку; системный диалог печатает или сохраняет в PDF.
  • Уведомления: колокольчик в шапке показывает напоминания об описи коробок и последние события журнала понятным текстом.
  • Адаптивность: на телефоне вкладки снизу, на ноутбуке тёмная боковая панель; светлая и тёмная темы; цвет каждого статуса один на всех экранах.

10. Развёртывание

Рис. 5. Окружение. Основной путь — пайплайн GitLab; ручная выкатка осталась запасной.
  • Образ: Dockerfile в корне, два этапа: сборка сайта (Node 22) и сервер (Python 3.11). При старте контейнер применяет миграции и запускает uvicorn; проверка живости /api/health.
  • Compose: deploy/docker-compose.yml поднимает app и caddy; имя сервера для HTTPS задаётся в deploy/.env (SITE_ADDRESS).
  • Адрес: https://hack-led-20-vm1-12902f.vmaas-spirit.t-education.com (сертификат Let's Encrypt).
  • Выкатка: автоматически из пайплайна после слияния MR в master (раздел 10). Запасной путь — rsync исходников и docker compose up -d --build (docs/DEPLOY_VM.md).
  • Локально: scripts/run-site.sh (сервер отдаёт API и сайт на порту 8000) или make dev + npm run dev.

11. CI/CD

Рис. 6. Пайплайн .gitlab-ci.yml по шаблону организаторов templates/l2sh-template.
  • Процесс: master защищён; изменения идут веткой и Merge Request. Пайплайн MR должен быть зелёным, после слияния пайплайн master сам выкатывает сайт.
  • Тесты в CI: сервер на SQLite с отчётом покрытия (cobertura, процент виден в GitLab) и те же тесты на PostgreSQL — там проверяется параллельная выдача номеров коробок; миграции вверх-вниз-вверх; сайт — vitest и сборка.
  • Выкатка: образ registry.spirit.t-education.com/hack-led-20/prod_1:<sha>; на ВМ копия базы в /root/backups, docker compose pull app и up -d в существующем стеке с Caddy, поэтому адрес и сертификат не меняются; deploy/.env, база и сертификаты не трогаются.
  • Проверка после выкатки: preflight:prod проходит весь сценарий ТЗ на живом сайте через демо-вход. Если он красный, пайплайн красный.
  • Отличия от шаблона: адреса culab.ru заменены на t-education.com (с раннеров не резолвятся), образ для ssh — kroniak/ssh-client, ключ SSH_PRIVATE_KEY очищается от \r.

13. Что не сделано и ограничения

  • Не реализованы план упаковки комнаты и опись коробки по фото из раздела 6 ТЗ (описаны в docs/API.md как развитие; опись по фото — только с явного согласия пользователя).
  • База — SQLite на одной ВМ. Резервные копии: каждый час по cron и перед каждой выкаткой (deploy/backup.sh: онлайн-копия, проверка целостности, последние 48 копий). Отказоустойчивости второй ВМ нет.
  • Нет восстановления пароля: почту не храним. Пароль можно сменить, зная текущий.
  • Номер удалённой последней коробки выдаётся снова (номер считается как max + 1).
  • Напоминания видны только в интерфейсе, без push и почты (осознанно: ТЗ не требует внешних каналов).
  • Камера сканера требует HTTPS (на ВМ включён); на реальном телефоне проверена, есть ручной ввод номера.
