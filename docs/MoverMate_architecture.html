1. Что делает система и какие у неё ограничения

Пользователь создаёт проект переезда (название, дата, адреса необязательны), получает готовый план задач на три этапа (до, в день, после), заводит коробки с комнатой назначения, быстро вписывает содержимое, печатает этикетки с QR-кодом, отмечает погрузку, доставку и распаковку и ищет вещи по названию. Если вещь потерялась, система подсказывает, в каких нераспакованных коробках её искать.

2. Общая схема

Рис. 1. Слои системы. Сайт и сервер едут в одном образе, база лежит в томе.

Сайт и API работают на одном origin: Caddy отдаёт сайт и проксирует /api на FastAPI, поэтому CORS не нужен. В режиме разработки запросы /api проксирует Vite (порт 5173 на порт 8000).

3. Сервер (backend)

Три слоя с чёткими обязанностями: роутер принимает и проверяет запрос, сервис содержит все правила и работает с транзакцией, модель описывает таблицы. Бизнес-правил в роутерах нет, поэтому сервисы можно тестировать без HTTP.

4. Модель данных

Рис. 3. Таблицы и связи. Миграция: backend/alembic/versions/0001_initial_schema.py.
  • Номер коробки хранится отдельным числом, а не как id. Сервер выдаёт max(number)+1 внутри проекта под блокировкой строки проекта; при гонке запись повторяется до трёх раз, а UNIQUE не даёт создать дубль. Удалённые номера не переиспользуются: напечатанная этикетка не должна указывать на чужую коробку.
  • name_norm в вещах: имя без регистра, ё = е, схлопнутые пробелы. Поиск не зависит от функций СУБД и одинаково работает на SQLite и PostgreSQL.
  • Комната это строка в коробке: у комнаты нет своих атрибутов, прогресс по комнатам считается группировкой.
  • Индексы: boxes(project_id, room, status), items(box_id), items(name_norm), tasks(project_id, stage), events(project_id, id).
  • Справочники (task_templates, tips) сидятся при каждом старте и добавляют только недостающее.

5. Доменная логика: статусы коробки

Рис. 4. Машина статусов. Таблица переходов: TRANSITIONS в services/boxes.py.

Проверка переходов вынесена в чистую функцию check_transition и покрыта тестом на все 25 пар статусов. Смена статуса, запись в журнал и проверки идут в одной транзакции со SELECT … FOR UPDATE по коробке: две одновременные отметки идут по очереди. Массовая погрузка комнаты (bulk-transitions) атомарна: один недопустимый номер отклоняет всю операцию.

Правила, на которых держится сервис

ОбластьПравило
ПоискСовпадения ранжируются: точное, с начала слова, вхождение; затем номер коробки и id. % и _ в запросе обычные символы
Прогресс«Погружено» в комнате = погружена + доставлена + распакована; «Распаковано» = распакованные / все коробки комнаты; охват описью = коробки с вещами / все
НапоминанияКоробка «заполнить позже», без вещей, срок не задан или наступил; вычисляются при запросе, без планировщика
Подсказки о потерянной вещиТолько нераспакованные коробки: где записана (1,0), где лежит похожее по основам слов (0,8), та же комната (0,6); не больше 10, порядок стабилен
Умный чек-листПравила для флагов «дети», «животные», «другой город» в reference_data.py; добавляются только отсутствующие по названию, срок считается от даты переезда
УдалениеВсегда с confirm=true, иначе 422: случайный запрос не удаляет данные

7. Сайт (frontend)

React 19, TypeScript, Vite, react-router-dom, обычный CSS без UI-библиотек. Зависимостей минимум, код короткий. Сканер QR (html5-qrcode) подгружается отдельным куском только при открытии экрана.

Как работают экраны

  • Каждый экран грузит данные через useAsync и показывает единые состояния «загрузка / ошибка с повтором / пусто» (StateView). Действия пользователя ловят ошибки сервера и показывают понятный текст.
  • Клиент API (api/client.ts) ходит на /api того же origin, ставит таймаут 20 секунд, разбирает формат ошибок сервера и превращает ответ nginx в HTML (502) в понятное сообщение.
  • Выбранный проект хранится в localStorage (с защитой от недоступного хранилища). Если открыли ссылку из QR на проект, которого нет в списке, он добавляется автоматически.
  • QR: этикетка кодирует обычную ссылку {origin}/projects/{pid}/boxes/{n}; QR рисуется в браузере (qrcode.react). Любая камера телефона открывает её; на сайте есть и свой сканер, который принимает ссылку с любым адресом сайта.
  • Печать: window.print() и правила @media print оставляют только этикетку; системный диалог печатает или сохраняет в PDF.
  • Адаптивность: на телефоне вкладки снизу, от 900 пикселей слева; светлая и тёмная темы; цвет каждого статуса один на всех экранах.

11. Что не сделано и ограничения

  • Пайплайн GitLab. Деплой пока вручную, а критерий жюри требует сборку и деплой из CI. В шаблоне организаторов (templates/l2sh-template) нужны: .gitlab-ci.yml с шагами build, test, deploy и переменные SSH_PRIVATE_KEY, DEPLOY_VM; сервис-аккаунт для образов в тенанте уже создан.
  • Код в GitLab организаторов ещё не отправлен (ждёт токен доступа).
  • Не реализованы план упаковки комнаты и опись коробки по фото (описаны в docs/API.md).
  • Участника нельзя удалить из проекта, а приглашение действует до истечения (7 дней); восстановления пароля нет: почту не храним.
  • База на одной ВМ (SQLite в томе), резервных копий нет. Параллельные запросы на PostgreSQL проверены только тестом, который в обычном прогоне пропускается.
  • Камера в браузере требует HTTPS: на ВМ он включён, на локальном запуске работает только на localhost. Саму камеру на телефоне ещё не проверяли.
