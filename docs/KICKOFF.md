# Старт: первые 4 часа после сбора команды и получения кейса

**Правила (подробно — `docs/RULES.md`):** на площадке быть не позднее 11:00 каждого дня (иначе риск дисквалификации), каждый участник коммитит под своим именем, защищает проект вся команда.

Когда команда в сборе и кейс выбран (по программе это 12:00–14:00 первого дня). Цель к концу первого рабочего блока (≈ 17:30):
**разобранный кейс, живая ссылка с деплоем и первая вертикаль «форма → API → БД → список» на проде.**
Подробное расписание по дням — в `PLAYBOOK.md`; здесь — что делать прямо сейчас и кто за что отвечает.

## Минуты 0–60: разбор (все вместе, один документ `docs/CASE.md`)

| Минуты | Что | Кто | Результат |
|---|---|---|---|
| 0–15 | Все читают ТЗ целиком. Каждый подчёркивает слова «должен», «обязательно», «минимум» | все | общий список требований |
| 15–25 | Заполнить **таблицу «Минимум из кейса»** в `CASE.md` дословно из ТЗ и объём данных (например «≥12 товаров, ≥5 заказов»). За невыполнение — штраф −30% | продакт пишет, остальные проверяют | таблица, где каждая строка — требование жюри |
| 25–35 | **«Что не нужно делать»** из ТЗ + наши решения (авторизация? оплата? ML?) | все | список «не делаем» |
| 35–45 | Сущности (3–6), роли, статусы, главный сценарий (5–7 шагов). Решить, какой тип кейса — см. таблицу ниже | бэкенд + продакт | схема данных на бумаге, ER-эскиз |
| 45–55 | Распределить работу (раздел «Роли» ниже) и договориться об **API-контракте**: пути и поля — на бумаге, до кода | бэкенд + фронтенд | список эндпоинтов, фронтенд может работать с заглушками |
| 55–60 | Вопросы для менторов и продакт-менеджеров (15:00): всё, что в ТЗ неясно | продакт | список вопросов в `CASE.md`, раздел 9 |

**Если ТЗ неоднозначно — не гадайте, спрашивайте менторов сразу.** Неверно понятый минимум стоит −30%.

## Тип кейса → что делать с шаблоном

| Если кейс про… | Что оставить | Что добавить | Оценка (допущение) |
|---|---|---|---|
| **Согласование/заявки/офферы** (статусы, роли, комментарии) | почти всё: `RULES`, история, роли, статистика | переименовать `Item` и поправить правила (чек-лист в `PLAYBOOK.md`) | 1–2 ч |
| **Витрина** (каталог, корзина, заказ) | авторизация (если нужна), список, поиск, фильтры | `Product`, `Order`, `OrderItem`, корзина на фронте | 5–7 ч |
| **Очередь, лимиты, таймеры** | роли, история, статистика | `Booking`/`Run`, позиция в очереди, параметр «текущее время» для «машины времени» | 3–4 ч |
| **QR, профили, знакомства** | роли, список, история | код события, QR на фронте, таблица «интересов», статистика организатора | 3–4 ч |
| **Алгоритм** (взаимозачёт долгов, сетка турнира, подбор комнат) | сущности, роли, тесты, история | чистая функция в `services/` (вход → результат) с **unit-тестами на сам алгоритм**; потом API и экран | 2–3 ч |
| **Расчёт по данным** (тариф, зарплата) | форма, API, тесты | загрузка CSV при старте, функция расчёта, метка «реальное/восстановленное» | 2–3 ч |

Оценки — мои допущения для одного разработчика, не данные организаторов.

## Роли на первые часы (4 человека; в команде из 3 — совмещайте, из 5 — добавьте дизайнера)

| Роль | Минуты 60–180 | Готово, когда |
|---|---|---|
| **Бэкенд** | переименовать сущность по чек-листу, миграция, правила, тесты на каждое правило | `make test` зелёный, Swagger показывает новые эндпоинты |
| **Фронтенд** | экраны по сценариям на заглушках, потом подключение к API по контракту | главный сценарий кликается, состояния «загрузка / ошибка / пусто» есть |
| **Платформа** (часто бэкендер, у вас) | **сервер и первый деплой пустого каркаса**, секреты, CI; затем `seed.py` под объём данных кейса | ссылка открывается, `scripts/preflight.sh` — 10 OK, CI зелёный |
| **Продакт / презентация** | `CASE.md` целиком, user stories, метрика (North Star), вопросы продактам | таблица минимума заполнена, метрика с формулой |

## Минуты 60–240: порядок работы платформы (самый важный трек)

0. **GitLab.** По Положению (п. 4.9) код сдаётся в GitLab организаторов: доступ, проект, `git push gitlab main`, переменные CI. Порядок — `docs/GITLAB.md`. Спросите про раннеры (общие на Docker или на сервере команды?).
1. **Сервер.** Спросили ментора, получили доступ? Да → `docs/DEPLOY.md`, путь 1. Нет → ждём до 15:00, параллельно работаем локально; к концу дня нет сервера → свой VPS или `make tunnel` (аварийно).
2. **Переменные CI в GitLab:** `DEPLOY_MODE`, `REMOTE_SERVER`, `DEPLOY_USER`, `SSH_PRIVATE_KEY`, `POSTGRES_PASSWORD`, `SECRET_KEY`, `ADMIN_PASSWORD` (список — `docs/GITLAB.md`). Запасной вариант на GitHub: секреты `DEPLOY_*` и `DEPLOY_ENABLED=true`.
3. **Первый деплой пустого каркаса — до 15:00.** Пока он не прошёл, не копите код: каждый пуш в `main` должен выкладываться.
4. Прогнать `scripts/preflight.sh http://<адрес>`, записать адрес и пароль админа в README («Как проверить»).
5. Дальше: демо-данные под кейс, автоматический деплой после каждого merge, ежевечерний `preflight`.

## Правила первого дня
- **Одна вертикаль, а не пять заготовок.** Лучше один сценарий насквозь на проде, чем много экранов без бэкенда.
- Merge в `main` — только при зелёном CI; ветки короткие.
- Вечером: что сломалось, что не успели, что вырезаем. Вырезать в 20:00 дешевле, чем в 12:00 третьего дня.

## Если что-то пошло не так

| Ситуация | Что делать |
|---|---|
| Сервер не дали и не дадут | свой VPS (`DEPLOY.md`, путь 4), на крайний случай `make tunnel`; сказать жюри честно |
| Положение запрещает готовый код или требует раскрыть шаблон | раскрыть в README и на презентации, что использован шаблон; если запрещает полностью — оставить только структуру и написать код заново по чек-листу |
| Кейс не ложится ни на один тип | взять модель «сущность со статусом + роли» как основу и считать расчёты отдельным модулем в `services/` |
| Бэкенд и фронтенд разошлись в API | единственный источник правды — Swagger (`/api/docs`) и `frontend/src/types.ts`; чинить сразу, не копить |
| CI красный, а нужно выкладывать | линтер деплой не блокирует; падают тесты — чинить, а не отключать |
| Не успеваем минимум | вырезаем всё, что не входит в минимум, и добиваем его; штраф −30% дороже любой фичи |
