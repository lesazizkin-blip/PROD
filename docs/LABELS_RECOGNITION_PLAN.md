## 3. Зафиксированные продуктовые идеи

### Два режима QR на уровне проекта

- **Универсальный QR**: полный URL, работает обычной камерой телефона и внутри MoverMate. Предлагаемый режим по умолчанию для существующих и новых проектов.
- **Компактный QR**: короткий идентификатор, работает встроенным сканером MoverMate. Цель — 10–20 символов полезной нагрузки, без полного URL.
- Настройка влияет на следующую генерацию этикеток. При переключении старые распечатки сохраняют работоспособность: сканер принимает оба формата постоянно.
- Плотность матрицы и физический размер — разные настройки. Рядом с выбором показать превью и пояснение, как сканировать.
- Не удалять служебные квадраты QR вручную, не фиксировать слишком малую версию, не снижать коррекцию ошибок без проверки реальной печати.

### Шаблоны этикеток

1. Стандарт: QR + крупный номер + комната.
2. Только QR: компактная наклейка без подписи.
3. Для заметок: QR + номер + свободное поле для рукописи.
4. Без QR: крупный номер + комната, дополнительное свободное поле по выбору.

Общие настройки: выбранные коробки, размер этикетки/QR, раскладка на A4, количество экземпляров, предпросмотр и системная печать/сохранение PDF. Начать с нескольких фиксированных размеров, а не произвольного конструктора.

### Нет принтера

Это отдельный пользовательский путь, а не только шаблон для печати. После создания коробки показать: «Напишите на коробке #001», рядом комнату, действие «Следующая коробка» и способ открыть её вручную или по фото. Не заставлять заходить в экран печати.

### Распознавание рукописного номера

Первый объём — цифры номера, написанного маркером, например `#01`, `#001`, `001`. Не распознавать произвольную опись вещей или комнату как обязательную часть этой функции.

Фото → выделение надписи → один или несколько кандидатов → проверка существования коробки в выбранном проекте → подтверждение пользователем → карточка. Нечитаемый результат не должен превращаться в придуманную коробку. Ручной ввод доступен всегда и принимает те же формы записи.

## 4. Предлагаемый общий контракт — зафиксировать перед параллельной реализацией

Этот раздел не меняет действующий `docs/API.md`. Окончательные схемы и ошибки внести туда перед backend-разработкой и дать обоим агентам один коммит контракта.

### Типы и QR

- `QrMode = 'universal' | 'compact'`.
- `LabelTemplate = 'standard' | 'qr-only' | 'notes' | 'no-qr'`.
- Проект получает `qr_mode`, по умолчанию `universal`; изменение разрешено владельцу. Это общая серверная настройка, а не только localStorage телефона.
- Предлагаемая компактная нагрузка: `MM1:` + 16 случайных символов Base32, всего 20 символов. Префикс версионирует формат. Не кодировать один номер без проекта и не обрезать UUID без проверки коллизий.
- Код постоянен для коробки, уникальность обеспечивается БД; при коллизии генерация повторяется. Для старых коробок — миграция с заполнением. Удалённый код не должен начать открывать новую коробку: не переиспользовать, при необходимости сохранять tombstone.
- Существующие `qr_path` и URL-маршрут сохраняются. В `LabelOut` добавить `qr_payload` с полной строкой для генератора. Пока новые поля не доступны, универсальный режим использует существующий `qr_path`; компактный режим нельзя тихо имитировать ссылкой.
- Предложение resolver: `POST /api/boxes/resolve-code`, body `{ code }`, ответ `{ project_id, box_number }`. Только чтение, без смены статуса и создания сущностей. Проверка сессии и членства; код не является пропуском в проект. Для чужого/неизвестного кода — согласованная ошибка без раскрытия карточки.
- Сканер: старый URL → существующий разбор; `MM1:...` → resolver. Неизвестный формат → понятное сообщение. Вход после скана сохраняет намерение открыть коробку; проверка доступа выполняется после входа.
- Публичные типы, функции разбора и builder выделить в `frontend/src/features/labels/contract.ts`; backend согласует соответствующие значения. Точное размещение интегратор может уточнить до старта агентов.

### Рукописный номер

- Рукописный номер разрешается только внутри явно выбранного проекта; показать его название рядом с камерой и подтверждением.
- Нормализация: разрешить один необязательный `#`, пробелы по краям и ведущие нули; после нормализации только целое положительное безопасное число. Проверять всю строку, а не извлекать произвольные цифры из мусора.
- Фото может содержать адрес, телефон или несколько номеров: показывать неоднозначность, не открывать первый попавшийся номер.
- OCR возвращает кандидаты, исходный распознанный текст и диагностические данные. Не показывать искусственный процент уверенности, если движок его не даёт или он не откалиброван.
- Фото и QR — взаимоисключающие режимы камеры: остановить один поток до запуска другого, освобождать камеру при уходе со страницы и возвращении из фона.
- Распознавание предлагается выполнять локально. Выбор библиотеки и модели — после прототипа на рукописных примерах. Не считать обычный печатный OCR доказательством поддержки почерка.
- Если локальный движок не проходит порог: зафиксировать результат и оценить другой движок. Внешний vision-сервис — отдельное решение пользователя с явным согласием на передачу фото. Ручной ввод остаётся рабочим, но сам по себе не считается завершённым распознаванием рукописи.

## 5. Этапы и критерии приёмки

### Этап 0. Контракт и воспроизводимый сбой

Интегратор фиксирует схемы раздела 4, единый базовый коммит и владение файлами. Уточняет в воспроизведении, где именно сбой: не декодируется QR, не открывается карточка, нет доступа или устарели данные.

Проверки: создать коробку на ноутбуке; на телефоне оставить старую вкладку; сканировать через сайт и обычную камеру; повторить с другим аккаунтом с приглашением и без него. Записать браузер/устройство, формат и размер QR, состояние сети, фактический результат, HTTP-ошибку при наличии. Не утверждать воспроизведение без устройства.

Готово: согласован контракт; определён способ сохранения настройки; подготовлены примеры обоих QR и набор фотографий номеров. Физические проверки, которые пока недоступны, явно отмечены.

### Этап 1A. Печать и генерация

- Один renderer для превью, одиночной и пакетной печати; четыре шаблона.
- Явное белое поле QR в 4 модуля, чёрный код на белом, размеры в mm при печати.
- Выбор всех/нескольких коробок, экземпляров и раскладки. Предлагаемые пресеты A4: 4 крупных, 8 средних или 12 компактных; фактическую геометрию подтвердить с учётом полей и минимального размера QR.
- Не перепечатывать все коробки для повторной печати одной этикетки. Настройки и выбранные коробки сохраняются при переходе в предпросмотр.
- Печатать только листы: без навигации, кнопок, заголовков приложения; не рвать этикетку; не создавать пустую последнюю страницу. Длинные названия и список вещей не выталкивают QR.
- Системный PDF допустим; отдельная серверная генерация PDF не требуется. Инструкция: бумага A4, фактический размер 100%, отключить колонтитулы браузера.

Приёмка: 1, 4, 9, 12 и 13 выбранных коробок; все шаблоны; длинная комната; пустой список; несколько экземпляров; просмотр на 375/768/1280 px; PDF соответствует превью; универсальный и компактный QR читаются после реальной печати. До готовности backend печать стандартного QR можно интегрировать отдельно.

### Этап 1B. QR-сканер

- Адаптивная область сканирования, задняя камера, повторный старт после отказа/сбоя; состояния «доступ к камере», «готово», «распознано», «открываем» и конкретная ошибка.
- Один переход на один успешный скан; защита от повторных callback и гонок start/stop, проверка StrictMode и ухода во время старта.
- Старые ссылки и короткие коды; resolver не зависит от выбранного проекта. Ошибки камеры, сети, авторизации и отсутствующей коробки различимы.
- Ручной номер: поддержка `#001`, видимый проект, корректная валидация.

Приёмка: оба формата, повторный скан без дублей, смена выбранного проекта, отказ камеры и повторное разрешение, нет сети, чужой код, удалённая коробка, возврат из фона. Автотест должен вызывать callback распознавания и проверять переход/resolver, а не только наличие заголовка.

### Этап 2. Рукопись без принтера — обязательная часть этого плана

Сначала короткий прототип распознавания в изолированном модуле, затем пользовательский сценарий. Оба агента могут работать одновременно: печать не ждёт исследования OCR.

Предлагаемый набор оценки: минимум 50 отдельных фото от 3 людей, минимум 15 отложенных для проверки без подстройки. Включить `#01`, `#001`, `10`, `100`, разные маркеры, картон/бумагу, наклон, тени, смазанные фото и несколько чисел. При разделении учитывать авторов/условия съёмки; не измерять качество только синтетическими шрифтами.

Предлагаемый порог для хороших читаемых фото: правильный номер присутствует среди не более 3 кандидатов минимум в 90% случаев на отложенном наборе. Отдельно записывать точность первого кандидата, ошибочные уверенные результаты, задержку и размер загрузки. Нечитаемые кадры проверять отдельно; не исключать сложные фото из отчёта незаметно. Это целевой критерий, не обещанная точность.

На целевых телефонах измерить первый запуск и повторное распознавание; целевой ориентир — до 3 секунд после готовности модели, без зависания интерфейса. Тяжёлое распознавание вынести в worker, модель подгружать по запросу, корректно обрабатывать отмену и ошибку загрузки.

Приёмка UX: «Нет принтера» → инструкция написать номер → камера «Распознать номер» → кадр и кандидаты → пользователь исправляет/подтверждает → свежая карточка с сервера. При низком качестве — переснять или ввести номер. Ни распознавание, ни подтверждение не создают коробку и не меняют её статус.

Завершение этапа требует отчёта по отложенному набору и проверки на телефонах. Если порог не достигнут, этап остаётся незавершённым; выпуск ручного ввода не закрывает OCR.

### Этап 3. Интеграция и финальная проверка

- Интегратор добавляет выбор QR в настройки проекта и путь «Нет принтера» после создания коробки.
- Обновляет видимые данные при возвращении во вкладку; не сбрасывает введённые формы и не создаёт запросы на каждом кадре камеры.
- Запускает backend-тесты контракта/миграции/прав доступа и `npm test`, `npm run lint`, `npm run build` на общем результате.
- Проверяет на iOS Safari и Android Chrome: QR с экрана и бумаги, рукопись, фоновая вкладка, поворот, повторный вход и чужой проект.
- Отмечает раздельно локальные автотесты, браузерную проверку, физические устройства, реальную печать и production. Обновляет `docs/CASE.md` только по фактическим результатам.

## 6. Параллельная разработка: два агента + интегратор

Рекомендованный вариант для этой задачи: два агента 6.1 Sol, отдельные worktree от одного коммита контракта. Это инженерный выбор, не сравнительный бенчмарк моделей. Luna можно поручить ограниченный модуль раскладки/fixtures/тесты; выбор OCR и управление камерой оставить одному ответственному, чтобы не получить две несовместимые реализации.

Codex App удобен для просмотра двух задач и diff; CLI также подходит с двумя отдельными worktree. Запускать два процесса в одном checkout нельзя: отдельные ветки без отдельных каталогов не изолируют незакоммиченные изменения. Наличие конкретных моделей проверить в выбранном интерфейсе перед запуском; названия CLI не угадывать.

Официальный обзор параллельных задач и worktree: https://developers.openai.com/blog/run-long-horizon-tasks-with-codex

Последовательность:

1. Интегратор фиксирует контракт и безопасную основу ветки, backend-владелец подтверждает серверный объём.
2. A делает шаблоны/раскладку; B параллельно стабилизирует QR и исследует OCR. Разработка использует контрактные fixtures, production работает только с реальным API.
3. Интегратор подключает backend и принимает A; первая контрольная точка — печать и надёжный универсальный QR.
4. Подключает компактные коды и настройку проекта; проверяет совместимость старых этикеток.
5. Принимает B и результаты рукописи; вторая контрольная точка — полный сценарий без принтера.
6. Общая проверка, отдельные исправления, затем решение о публикации. Агенты сами не деплоят и не сливают свои ветки.

Оценивать сроки после этапа 0 и OCR-прототипа. Печать и стабилизация QR предсказуемее; распознавание почерка — главный риск по времени и качеству.
