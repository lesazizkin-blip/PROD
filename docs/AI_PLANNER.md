# Персональный план при создании переезда

Форма `/new` и создание первого проекта: название, дата, необязательное описание потребностей
текстом или голосом. После явного согласия кнопка запрашивает персональные дополнения к
стандартному плану. Пользователь редактирует названия, этапы, сроки и список первого дня,
удаляет лишнее и нажимает «Создать проект». До этого БД не меняется.

## Настройка сервера

Используется совместимый с Chat Completions HTTP API. Нужны поддержка
`response_format: {"type":"json_object"}` и параметра `max_tokens`, JSON в
`choices[0].message.content`. Поддержка всех провайдеров/моделей не подразумевается.
URL и модель выбирает администратор, сайт не позволяет пользователю их подменять.

В `deploy/.env`:

```dotenv
AI_API_KEY=<ключ аккаунта LLM Proxy в Spirit>
AI_BASE_URL=https://llm-proxy.spirit.t-education.com
AI_MODEL=openrouter/google/gemini-3.1-flash-lite
AI_REQUESTS_PER_HOUR=10
```

`AI_BASE_URL` — HTTPS, без `/chat/completions` в конце, query и учётных данных.
При локальном запуске переменные задаются в окружении backend или `backend/.env`.
Оба Compose-файла передают настройки серверу. Переменные `VITE_*` для ключа не используются.
Никогда не коммитить `.env` и не присылать ключ в чат.

Это рекомендуемый стартовый профиль из предоставленного каталога Spirit (52 модели).
Gemini 3.1 Flash Lite ориентирована на низкую задержку и поддерживает структурированный
вывод; качество русскоязычных планов через Spirit ещё не измерено. Наличие модели в
каталоге не означает, что у конкретного аккаунта есть квота на неё.

Подключение Spirit:

1. Откройте тенант → AI → LLM → Аккаунты → нужный аккаунт и проверьте квоту выбранной модели.
2. Создайте ключ аккаунта и сохраните только в серверном `deploy/.env` как `AI_API_KEY`.
   Для прокси нужен ключ Spirit; отдельный ключ Google или OpenRouter не требуется.
3. Передавайте полный идентификатор `openrouter/google/gemini-3.1-flash-lite`, включая
   префикс `openrouter/`. Наш адаптер добавляет `/chat/completions` к `AI_BASE_URL`,
   использует `Authorization: Bearer ...` и стандартный JSON Chat Completions.
4. Выполните проверку на тестовом проекте после развёртывания. Без ключа живой вызов
   не проверен; автотест проверяет URL, идентификатор модели, авторизацию и формат запроса
   на `httpx.MockTransport`.

Корневой URL выше взят из конкретного примера Chat Completions в документации Spirit;
в разделе провайдеров также указан `/v1`, а для Responses пример использует `/v1/responses`.
Не переносите префиксы разных API в настройки без проверки.

На момент чтения документация Spirit сообщает, что маскирование критических данных
временно не работает. Не рассчитывайте на автоматическое удаление личных сведений:
описание пользователя передаётся как есть, адреса и инвентарь из БД не отправляются.

Источники:

- [Spirit: аккаунты и ключи](https://docs.pages.t-education.com/docs/docs/ai/llm-proxy/accounts)
- [Spirit: квоты и ошибки](https://docs.pages.t-education.com/docs/docs/ai/llm-proxy/limits-and-errors)
- [OpenRouter: Gemini 3.1 Flash Lite](https://openrouter.ai/google/gemini-3.1-flash-lite)

После интеграции ветки и настройки сервера:

```bash
cd deploy
docker compose up -d --build app
```

Проверить на сайте: создать отдельный тестовый проект, описать конкретные потребности,
получить черновик, изменить задачу, создать проект и обновить страницу.
В запросе браузера к `/api/projects/plan-preview` не должно быть ключа провайдера;
браузер обращается только к своему backend. Затем удалить тестовый проект через обычный UI.

Пустые настройки дают понятную ошибку и сохраняют возможность создать стандартный проект.
Timeout HTTP-провайдера по умолчанию 12 секунд на сетевую операцию (настройка
`AI_TIMEOUT_SECONDS`, до 15); у браузера общий таймаут 20 секунд.
Автоматических повторов платных запросов нет. Лимит генераций — в памяти одного процесса;
для нескольких workers/реплик потребуется общий лимит на шлюзе или в БД.

## Приватность и проверка

Перед отправкой показано согласие на передачу описания и даты внешнему AI-сервису.
Не включайте в описание адреса и личные сведения. Из БД никакие данные не отправляются;
написанные самим пользователем сведения в описании передаются как есть. Описание не
сохраняется в БД; остаются только одобренные задачи и пункты первого дня.
Ответ модели — недоверенный черновик, валидируется Pydantic и не выполняет действий/команд.
Генерация не добавляет коробки, участников и не меняет чужие проекты.

Диктовка использует `SpeechRecognition`/`webkitSpeechRecognition`, `ru-RU`, только финальный
результат. При закрытии компонента распознавание прекращается. Аудио не загружается
на backend MoverMate, но браузер может использовать внешний сервис распознавания.
На неподдерживаемом устройстве доступен текст и диктовка экранной клавиатуры.

## Проверки разработки

```bash
cd backend
python -m pytest
ruff check app tests
ruff format --check app tests
cd ../frontend
npm test
npm run lint
npm run build
```

Нужен Node.js, совместимый с текущей Vite (проверялось на Node 24).
Тесты провайдера используют `httpx.MockTransport`, не платный API.
Браузерная проверка на локальном backend: отсутствие ключа, редактирование тестового ответа,
реальное создание/сохранение задач, перезагрузка, desktop 1440×1000 и mobile 390×844.
Успешная генерация в browser QA использует fixture; настоящий провайдер и реальный микрофон
должны быть проверены на целевом устройстве после настройки. Качество модели не измерено.

Изменения подготовлены в `feat/ai-moving-planner` от `f4071ab`. В основной рабочей копии
есть незавершённые изменения компактных QR, в том числе в `schemas.py` и `services/projects.py`.
При интеграции сохранить их `qr_mode` и существующую логику; AI-добавления не требуют миграции БД.
