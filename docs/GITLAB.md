# GitLab: как сдавать код и запускать CI на хакатоне

По Положению (п. 4.9) решения команд размещаются на **GitLab организаторов**. У призёров прошлых хакатонов в каждом репозитории лежал `.gitlab-ci.yml`;
шаблон содержит такой же файл (`.gitlab-ci.yml` в корне). GitHub-репозиторий остаётся вашей личной копией и запасным вариантом (там CI на GitHub Actions).

## Первые шаги (платформа, первый час)
1. **Получить доступ к GitLab** у менторов: адрес, учётные записи, группа или проект. Каждый участник заходит **под своим аккаунтом**.
2. **Создать проект** (если его не создали организаторы) и **отправить туда шаблон**:
   ```bash
   git clone git@github.com:<вы>/prod-hackathon-ml.git   # свежая копия шаблона
   cd prod-hackathon-ml
   git remote add gitlab <адрес-проекта-в-GitLab>        # или: git remote set-url origin <адрес>
   git push gitlab main
   ```
   Остальные участники клонируют уже GitLab-проект. Ветки короткие, merge в `main` через Merge Request.
3. **Каждый коммитит под своим именем** (`git config user.name/email`): Положение требует «весомого вклада» каждого.
4. **Узнать у менторов про раннеры** (это определяет режим CI):

   | Вопрос | Если «да» | Если «нет» |
   |---|---|---|
   | Есть общие раннеры (shared runners) на Docker? | `RUNNER_MODE` не задаём (режим `docker`) | спросить про раннер на сервере |
   | Есть раннер на сервере команды (тег вроде `self-hosted`)? | `RUNNER_MODE=shell`, `DEPLOY_MODE=local` | деплой по SSH (`DEPLOY_MODE=ssh`) |
   | Раннер привилегированный (Docker-in-Docker)? | задание `stack-dind` заработает | оно упадёт и **не блокирует** остальное |
   | Какой тег у раннеров? | если не `self-hosted`, поправить `tags:` в `.gitlab-ci.yml` | |
   | Есть Container Registry? | пригодится для хранения образов (в шаблоне пока не используется) | |

## Переменные CI (Settings → CI/CD → Variables)
| Переменная | Зачем | Заметки |
|---|---|---|
| `DEPLOY_MODE` | `ssh` или `local`; без неё деплоя нет | включайте, когда сервер готов |
| `RUNNER_MODE` | `shell` для раннера на сервере; по умолчанию docker | |
| `REMOTE_SERVER`, `DEPLOY_USER` | куда и под кем заходить (режим `ssh`) | |
| `SSH_PRIVATE_KEY` | приватный ключ для входа на сервер | лучше тип **File**; публичная часть — на сервере; **Protected** |
| `DEPLOY_PORT`, `DEPLOY_SSH_PORT` | порт сайта (по умолчанию 80) и порт SSH (если не 22) | |
| `POSTGRES_PASSWORD` | пароль БД | **только латинские буквы и цифры**; Masked |
| `SECRET_KEY` | подпись токенов | не короче 32 символов; Masked |
| `ADMIN_PASSWORD`, `ADMIN_EMAIL` | администратор | не короче 8 символов, не `admin12345`; Masked |
| `SEED_DEMO` | `false` — без демо-данных | по умолчанию `true` |

Приложение в режиме `production` не стартует с пустыми или публичными секретами: деплой завершится ошибкой с понятным сообщением, а не выложит небезопасный сервер.

## Что делает пайплайн
| Задание | Стадия | Что |
|---|---|---|
| `lint-backend`, `lint-frontend` | lint | стиль кода; **деплой не блокируют** (`make fmt` чинит) |
| `test-backend` | test | тесты на SQLite и на PostgreSQL (сервис), миграции вверх-вниз-вверх; **процент покрытия и отчёт о тестах видны в GitLab** |
| `test-frontend` | test | тесты и сборка фронтенда |
| `stack-dind` | build | весь стек в Docker + `preflight.sh` (нужен привилегированный раннер; не блокирует) |
| `test-shell` | test | то же на раннере сервера (`RUNNER_MODE=shell`) |
| `deploy-ssh` | deploy | вход на сервер по SSH, `docker compose up`, ожидание старта и `preflight.sh` (только `main`) |
| `deploy-local` | deploy | деплой с раннера, установленного на сервере (`DEPLOY_MODE=local`) |

## Что проверено
Задания прогнаны локально инструментом `gitlab-ci-local` (в Docker, образы `python:3.11`, `node:22`, `postgres:16`): `lint-backend`, `lint-frontend`, `test-backend` (покрытие 98%), `test-frontend` и `deploy-ssh` (на искусственном Ubuntu-сервере, до `preflight.sh` 10 из 10).
**Не проверено:** на настоящем GitLab ничего не запускалось; `stack-dind`, `test-shell` и `deploy-local` не запускались (нужны привилегированный раннер и раннер на сервере). Теги раннеров и права могут отличаться: первый запуск на хакатоне, скорее всего, потребует правок `tags:`.

Запустить задание у себя: `npx gitlab-ci-local test-backend` (нужен Docker; список заданий — `npx gitlab-ci-local --list`).

## Два репозитория
- **GitLab** организаторов — для сдачи и проверки жюри.
- **GitHub** — личная копия и запасной вариант (`.github/workflows/ci.yml`). Чтобы пушить в оба: `git remote set-url --add --push origin <адрес GitHub>` и `git remote set-url --add --push origin <адрес GitLab>`, затем обычный `git push`.
