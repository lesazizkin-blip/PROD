# Функции сверх минимума ТЗ

Минимум ТЗ и где он проверен — `docs/CASE.md`. Здесь — дополнительные функции: как работают, как включаются и чем ограничены.

## 1. Путь переезда: от решения до «обжились»

Страница `/journey` (видна и гостю) ведёт по семи этапам и показывает, где в сервисе каждый шаг.

| Этап | Что делает сервис | Где |
|---|---|---|
| 1. Решение | Калькулятор: коробки, объём, машина, грузчики, часы, бюджет «от–до», срок подготовки, советы по дате | `/calculator` (после входа), `POST /api/calculator` |
| 2. Новое жильё | План «Снимаю или сдаю квартиру»: осмотр, фото «до», счётчики, подъезд для грузовика, акт, залог | Умный чек-лист → `renting` |
| 3. Подготовка | ИИ-план с уточняющими вопросами; планы «Документы и смена адреса», «Разобрать вещи», дети, питомцы, другой город | Умный чек-лист, создание проекта |
| 4. Подрядчики | Вне сервиса: смета калькулятора — основа заказа | — |
| 5. Упаковка | Коробки, опись и раскладка по фото, QR-этикетки, поиск, первый день | «Коробки», «QR-этикетки» |
| 6. День переезда | Статусы «Погружена» и «Доставлена», чек-лист погрузки комнаты, прогресс; повреждения — статус вещи | «Коробки», «Прогресс» |
| 7. Обжиться | План «Обжиться после переезда»; итог: задачи, доехавшие и распакованные коробки, потери, бюджет | «Прогресс» → «Итог переезда» |
| Сквозное | Бюджет «план–факт» по статьям с отклонением | `/budget`, `/api/projects/{pid}/expenses` |

**Калькулятор** (`POST /api/calculator`, только после входа, без 401 не отвечает): ввод — город (`GET /api/cities`, 16 крупных городов), комнат 1–8, человек 1–10, расстояние 0–500 км, этажи 0–100 с лифтом и не выше 15-го без лифта, лифт, питомцы, пианино, хрупкое, дата; вне пределов, другой тип или неверная дата — 422, лишние поля игнорируются. Форма на сайте ограничивает ввод теми же пределами. Больше 100 км — перевозка между городами (по километрам); если работы больше 10 часов, совет разбить переезд на дни. Тело запроса больше 8 МБ отсекает Caddy (413), частоту — общий лимит запросов с IP.

**Откуда цены.** Ставки грузчиков и Газели с водителем — по городу из таблицы `city_prices` (миграция `0009`), данные Профи.ру: на страницах «Стоимость грузчиков» и «Стоимость газели на час» каждого города площадка публикует вилку ставок исполнителей и их число (разметка schema.org `lowPrice`/`highPrice`/`offerCount`). Проверено 17.10.2026; источник и числа — `backend/app/reference_data.py` (`CITY_PRICES`), таблица обновляется при старте приложения. В расчёте нижняя граница — минимальная ставка, верхняя — середина вилки (максимум площадки — крупные машины и премиум). Машина крупнее Газели дороже по тарифной сетке перевозчика: 18–20 м³ ×1,1, 35 м³ ×2,1, две машины ×2,2. Без города — средние по 16 городам. Коробки, упаковка, уборка, пианино, питомец и межгород за километр — средние по России в `services/calculator.py`. Источник и дата показываются под итогом.

Калькулятор — ориентир и ничего не сохраняет. Бюджет — таблица `expenses` (миграция `0008_expenses`), удаление расхода только с `?confirm=true`.

## 2. ИИ-помощник (LLM-прокси Spirit)

Три функции, все только по явному согласию пользователя; ответ модели — черновик, в проект попадает лишь то, что пользователь проверил и сохранил.

| Функция | Где на сайте | Ручка |
|---|---|---|
| Персональный план с уточняющими вопросами | создание проекта (`/new`): описание текстом или голосом → «Предложить персональный план» | `POST /api/projects/plan-questions`, затем `POST /api/projects/plan-preview` |
| Опись коробки по фото | карточка коробки → «+ Вещи» → «Заполнить по фото» | `POST /api/projects/{pid}/boxes/{n}/photo-inventory` |
| Раскладка комнаты по фото | «Коробки» → «Комната по фото» | `POST /api/projects/{pid}/room-plan` |

**План в два шага.** Модель задаёт до 3 вопросов с 2–4 вариантами (лифт и этаж, разборка мебели, животные), не спрашивая сказанное и личные данные. Пользователь отвечает, пишет свой вариант или пропускает. Затем `plan-preview` с `answers` (до 5, по 200 символов) строит 6–10 задач и до 6 вещей первого дня. Черновик редактируется; проект и задачи создаются только по «Создать проект». Описание в базе не сохраняется.

**Фото.** Тело `{"image": "data:image/jpeg;base64,...", "consent": true}` (+ `"room"` для комнаты). Фото уменьшается в браузере до 1280 px JPEG (EXIF с геопозицией не уходит), сервер проверяет тип (JPEG/PNG/WebP), base64 и размер до 4 МБ **до** списания попытки, передаёт модели один раз и не хранит. Опись отмечает вещи «первый день» и «хрупкое»; раскладка предлагает до 10 коробок, создаются только выбранные. Повторы модели убираются.

**Две модели.** План и вопросы — `AI_MODEL` (на проде Haiku, ключ `AI_API_KEY`). Фото — `AI_VISION_MODEL` (на проде Sonnet, ключ `AI_VISION_API_KEY`, если модель на другом аккаунте Spirit); не задана — фото тоже идут в `AI_MODEL`. Адрес общий: `AI_BASE_URL=https://llm-proxy.spirit.t-education.com/v1` (именно с `/v1`; без него прокси отвечает 404).

**Настройка на ВМ** (ключи вводятся скрыто, в чат и в git не попадают):
```bash
scripts/ai-setup.sh                          # AI_API_KEY, AI_BASE_URL, AI_MODEL → deploy/.env на ВМ, перезапуск app
scripts/vm-env.sh AI_VISION_MODEL            # вторая модель для фото
pbpaste | scripts/vm-env.sh AI_VISION_API_KEY  # её ключ из буфера обмена
```
Остальные переменные: `AI_REQUESTS_PER_HOUR=10`, `AI_GLOBAL_REQUESTS_PER_DAY=50` (0 отключает ИИ), `AI_TIMEOUT_SECONDS=45` (максимум 60). Без настроек сайт показывает понятную ошибку, стандартный план создаётся как обычно.

**Границы и безопасность:**
- Лимиты в базе: 10 попыток на пользователя в час и 50 на всё приложение в сутки (UTC); попытка списывается до обращения к прокси, в том числе при ошибке. План с вопросами тратит 2 попытки. Автоматических повторов нет.
- Модель, адрес, `max_tokens` (план 3000, вопросы 800) задаёт сервер; подставленные клиентом `model`, `tools`, `messages`, `base_url` игнорируются. Ключ не уходит в браузер.
- Ответ проверяется схемой Pydantic (не больше 30 задач, 20 вещей, 30 000 символов) и не выполняет действий.
- Из базы модели ничего не отправляется: только то, что пользователь написал или сфотографировал. Маскирование персональных данных на стороне Spirit на момент проверки не работало — в описании не стоит писать адреса и личные данные.
- Доступ только участникам проекта: чужой проект или несуществующая коробка — 404 без вызова модели.
- Ошибки провайдера различаются кодами `planner_credentials_invalid`, `planner_access_denied`, `planner_quota_missing`, `planner_provider_limit`, `planner_endpoint_not_found`; в журнал — только категория и статус, без тел запросов и ключа. Аудит: `ai.photo_inventory`, `ai.room_plan` (числа, без содержимого).
- Диктовка — `SpeechRecognition` браузера (`ru-RU`); аудио на наш сервер не идёт, но браузер может использовать свой внешний сервис.

Тесты без платных запросов (`httpx.MockTransport`): `test_planner.py` (в том числе попытки подменить модель, роль, «вызови 1000 раз», выдать ключ), `test_ai_budget.py` (50 параллельных резерваций не превышают лимит), `test_plan_questions.py`, `test_ai_photo.py`; на сайте — `PersonalPlanner.test.tsx`, `PhotoPicker.test.tsx`. На проде 17.10: вопросы 3,4 с, опись по фото 3,8 с, раскладка комнаты 11 с.

## 3. Этикетки и QR

**Шаблоны** (`/labels`): стандарт (QR + крупный номер + комната — обязательный по ТЗ), только QR, с полем для заметок, без QR. Выбор коробок и числа экземпляров, A4 на 4/8/12 этикеток, предпросмотр, печать или PDF из браузера без пустых страниц. QR генерируется в браузере (`qrcode.react`), белое поле в 4 модуля. Печать: A4, масштаб 100%, без колонтитулов.

**Два формата QR на уровне проекта** (переключает владелец на странице этикеток, видно на всех устройствах):
- универсальный (по умолчанию) — ссылка на карточку коробки, открывается любой камерой телефона;
- компактный — `MM1:` + 16 символов Base32 (20 символов, матрица 29×29 против 45×45), открывается встроенным сканером через `POST /api/boxes/resolve-code` (проверяет вход и участие в проекте).

Код коробки постоянный (`box_qr_codes`, миграция `0004_compact_qr`), уникальность обеспечивает база; код удалённой коробки не переиспользуется. Сканер принимает оба формата всегда, поэтому переключение не ломает старые распечатки. `VITE_COMPACT_QR_ENABLED=false` при сборке скрывает компактный формат.

**Сканер** (`/scan`): задняя камера, адаптивная рамка, один переход на один скан, понятные ошибки камеры, сети, доступа и отсутствующей коробки; камера освобождается при уходе и сворачивании. Ручной ввод номера `#001`/`001`/`1` в выбранном проекте; номер проверяется целиком, цифры из мусора не извлекаются.

**Нет принтера:** в карточке коробки — инструкция написать номер маркером (`#001`) и открыть коробку вручную или камерой.

Тесты: `frontend/src/features/labels/`, `ScanPage.test.tsx`, `backend/tests/test_compact_qr.py`.

## 4. Распознавание рукописного номера (экспериментально, выключено)

Локальный OCR (Tesseract.js в web worker, без передачи фото наружу): фото или «Камера номера» → выделение строки → кандидаты → проверка, что коробка есть в проекте → подтверждение пользователем → карточка. Камера номера обрабатывает кадр раз в 0,5 с и показывает номер только после совпадения на двух кадрах. Распознавание не создаёт коробки и не меняет статусы.

Качество почерка **не проверено**: на двух примерах одного почерка (`#001`, `#002`) путь работает, первый результат около 2 с, повторный около 0,9 с на ноутбуке; телефоны и другие почерки не проверялись. Поэтому в обычной сборке OCR выключен, доступен ручной ввод.

Включить на отдельном стенде:
```bash
cd frontend && npm ci
npm run prepare:ocr -- /absolute/path/eng.traineddata.gz   # проверяет SHA-256 и копирует worker/WASM/модель в public/recognition/ (не в git)
VITE_LOCAL_OCR_PROTOTYPE=true npm run dev
```
Модель: `https://tessdata.projectnaptha.com/4.0.0/eng.traineddata.gz`, SHA-256 `ed350f3752f81ee8f38769edc14d92d997dababe23b565c59879372cc46a2468`; команда подготовки не скачивает файл, а берёт локальный. Зависимости закреплены: `tesseract.js@6.0.1`, `tesseract.js-core@6.1.2`.

Что нужно для приёмки: не меньше 50 фото от 3 людей (15 отложенных), цель — правильный номер среди 3 кандидатов в 90% читаемых фото и до 3 с на телефоне.
