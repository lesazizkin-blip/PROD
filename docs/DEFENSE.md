# Шпаргалка: критерии, план на 3 дня, защита

## Как оценивают (по материалам прошлых хакатонов PROD)

Блоки: **Backend**, **Frontend/Mobile**, **Product**, общее впечатление и структура презентации. Критерии — по 0–2 балла.
**Штрафы:** решение не задеплоено — **−20%**; не выполнен минимум из кейса — **−30%**. Поэтому: сначала живая ссылка, потом фичи.

**Backend (база):** деплой + Swagger по URL и CI/CD · OpenAPI с примерами · схема данных + миграции · тесты (unit на ключевые сценарии, интеграционные, хотя бы один негативный, отчёт в CI) · диаграммы доменных процессов.
**Backend (продвинутые):** слои и качество кода · БД (индексы, N+1, транзакции) · эволюция логики (схема → код → API → тесты → миграции, логи, диагностика 500).
**Frontend (база):** деплой по CI/CD · запросы к бэкенду, данные синхронны с UI · UX (предсказуемые элементы, нет «мёртвых» кнопок, валидация ввода) · единый стиль · адаптивность.
**Product:** проблема и пользователь · user path и user stories · бизнес-ценность посчитана · понятный UX · главная метрика (North Star) и способ проверки гипотезы.

## «Мини-правки» на защите — готовые рецепты

Жюри просит внести небольшое изменение прямо при вас. Тренируйтесь заранее.

| Просят | Делаем |
|---|---|
| Новый статус / переход | `schemas.py` (Status/Action) → строка в `RULES` → тест → при необходимости метка во `frontend/src/labels.ts` |
| Новое поле в сущности | `models.py` → `make migration m="add field"` → схемы → тест → форма на фронте |
| Индекс / оптимизировать запрос | `models.py` (`Index`) → миграция; показать запрос в `repositories/` |
| Логика из контроллера в сервис | перенести в `services/`, роутер оставить тонким |
| Новый тест-кейс | скопировать похожий из `tests/`, поменять вход/ожидание, `make test` |
| Показать логи после запроса | запрос в Swagger → `make logs` / `docker compose logs backend` → найти по `request_id` |
| «Что делать при 500 после релиза?» | клиент получает `request_id` → ищем в логах traceback → воспроизводим тестом → правим → CI → деплой |
| Новое правило валидации | pydantic `Field(...)` в `schemas.py` + проверка на форме |

## Защита (5 минут)

1. Проблема и пользователь (30 с). 2. Живое демо главного сценария (1,5 мин). 3. Архитектура и решения — слои, БД, процесс (1 мин). 4. Качество: тесты, CI/CD, логи (1 мин). 5. Бизнес-ценность и метрика (1 мин).

Вопросы, к которым стоит быть готовыми: почему такие слои; как добавить новый статус; где возможен N+1 и зачем индексы; зачем транзакция при смене статуса; что произойдёт при 500 и где смотреть логи; как обновить OpenAPI; почему чужая запись отдаёт 404.
